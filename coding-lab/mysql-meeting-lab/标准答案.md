# 大纲四 · 口答标准答案

完整代码在src/main/java/com/wufeng/meeting/answer/ReferenceSteps.java；运行answer profile才启用。以下是口答参考，不是通过状态。

## 第1关

1. 单条查询快不代表链路快：循环放大网络往返与SQL执行，无索引又重复扫描几十万关系，串行通知另有300次等待。Controller识别请求，Service分段计时，Repository记录SQL数量/计划，结合连接池与上游延迟定位。
2. 一人可以参与多个议题，320条关系按person_id用Set合并成300人。真实通知还需约定按人、渠道和通知类型去重。
3. 查议题1次、8个议题分别查人8次，共9；本实验不计建连接/造数DDL。议题增多，逐查次数和返回量增加；IN在500以内仍一条，但处理人数仍会增长。
4. 分别统计查询与通知耗时、SQL次数、EXPLAIN/实际执行、线程池队列拒绝和连接池等待。一次只改一个变量，跑多轮，不用总耗时猜原因。

## 第2关

1. 常见system/const→eq_ref→ref→range→index→ALL；要结合实际扫描量。ALL扫表，index扫整棵索引，覆盖时可能更小，但并不自动高效。
2. possible_keys是候选，key是最终使用的索引；key空可能没可用索引，也可能全扫成本更低。结合SQL与数据分布分析。
3. rows为统计信息估算的扫描数，filtered是过滤后保留比例估算；采样/选择率/过期统计都会导致偏差，不是精确COUNT。EXPLAIN ANALYZE会实际执行查询，可用于校核。
4. filesort是不能直接借索引提供顺序，不等于一定落盘；temporary表示临时表，不一定磁盘；Using index常指覆盖索引，Using index condition指索引条件下推，二者不同。本例不要凭空补filesort/temporary。

## 第3关

1. topic_id二级B+树定位叶子区间，避免全表扫描；叶子含主键而不含person_id，可能需回表。可讨论(topic_id,person_id)覆盖，但本关只加普通索引便于区分机制。
2. 索引降低每次查找扫描量，IN降低SQL次数和往返；分无索引逐查→有索引逐查→有索引批查三阶段才看得清贡献。
3. ref表示非唯一等值定位，IN可形成多个等值区间而用range。不能仅按type排名断言IN更慢，要看总工作量、往返和实测。
4. 大IN增加报文、解析/区间构造、返回量与内存，可能改变计划。500是实验阈值，不是数据库上限，需压测。JdbcTemplate用占位符绑定，管理连接/语句/结果集；事务内获取Spring绑定连接，不能关闭整个DataSource。

## 第4关

1. core/max、keepAlive、unit、queue、factory、handler七项。先创建至core，再排队，队列满再扩至max，再拒绝。实验8/8/30/SECONDS/512，core=max时不会扩容，核心默认不按keepAlive退出。IO等待可粗估等待/计算比，再按上游限流、连接数、队列等待压测，不把CPU×2当公式答案。
2. Abort抛异常；CallerRuns提交者执行（关闭后不执行）；Discard静默丢当前任务；DiscardOldest丢队头后重试提交。本接口要可见拒绝、不占请求线程执行慢通知，所以计数后抛异常。拒绝要在submit当场捕获，不是只在Future.get捕获。
3. submit用FutureTask包装，异常存入Future，get抛ExecutionException，工作线程通常继续，忽略Future会漏异常。execute的Runnable未捕获异常可使工作线程退出并由池按需补充；任务自己捕获异常则不因此退出。
4. Spring共享池服务多个HTTP请求，不能每次结束关闭。中断只取消本次Future，purge清取消的排队任务，恢复中断标志；不取消其他请求任务。应用关闭由Spring销毁池。取消不保证远端HTTP没处理，真实客户端需连接/读取超时。

## 第5关与重试

1. 单条自动提交300SQL/300事务；8线程并发仍300/300，只重叠执行；每100条多VALUES共3SQL/3事务，减少往返与提交，但每批锁持有更久、失败回滚范围更大，之前已提交批次不回滚。JdbcTemplate用Hikari复用连接，不能把这里的耗时等同于独立程序每次建连接的指标。
2. TransactionTemplate开启事务，JdbcTemplate使用线程绑定连接，回调异常回滚该批。同类自调用@Transactional可能绕过代理；本demo直接用模板表达批次边界。事务不自动跨线程传播。线程过多会竞争连接、CPU、redo/fsync和锁，应观察等待与吞吐再限制并发。
3. 锁等待不一定成环，死锁有循环依赖；InnoDB检测后选牺牲事务，常见1213。锁等待超时常见1205。看SHOW ENGINE INNODB STATUS的LATEST DETECTED DEADLOCK、事务/SQL/索引锁，当前等待可看performance_schema.data_locks/data_lock_waits。1213要有限次数退避重试整笔业务事务；统一加锁顺序、缩短事务、合理索引降复发概率，不保证绝不死锁。
4. (meeting_id,person_id)唯一键约束一会一人一日志并定位记录；(status,create_time)服务按失败状态与时间扫描。索引也增加写入和页维护成本。日志唯一并不保证外部通知幂等：发送成功落库失败仍可能重发，要渠道幂等键/回执核对/补偿。仅加载指定会议FAILED重试，有限次数退避；本demo只重试一次，第二次mock成功，没有后台生产调度。
