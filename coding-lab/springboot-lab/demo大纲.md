## 大纲一 · 统一待办聚合（JUC 线程池）：从串行到并发

> ⚠️ **这个排在最后做**。先做下面的**大纲四**，再做**大纲五**，最后回到这里。（文件顺序是按历史排的，不是执行顺序。）

**场景锚点（真实的那个）**：集团门户首页要展示 OA / ERP / HR / FIN 四个系统的待办。
原实现是串行调用，光上游就约 470ms，任一系统抖动整页跟着卡。

### 第 0 关 · 热身：先把"_提交任务 → 拿 Future → get 结果_"这条链路跑通

- **做什么**：固定线程池，把 4 个上游并发跑完，打印全部待办和总耗时。
- **验收**：8 条待办齐全，总耗时 < 200ms。
- **要能答**：线程池提交任务后，线程是怎么复用的？为什么不是每个任务 new 一个线程？

### 第 1 关 · 手写 7 个参数

- **做什么**：把 `Executors.newFixedThreadPool(n)` 换成手写 `ThreadPoolExecutor`，7 个参数自己定。
- **要能答**：核心线程数为什么是这个数？队列为什么**必须**有界？拒绝策略选的哪个、什么时候会被触发？
- **面试追问**：执行顺序到底是"核心线程 → 队列 → 非核心线程 → 拒绝"，还是"核心满了就开非核心"？为什么阿里规约禁止用 `Executors`？

### 第 2 关 · 超时控制

- **做什么**：给每个上游加 250ms 超时。
- **要能答**：`get(timeout)` 超时返回之后，那个还在跑的上游任务会不会被中断？进程要多久才能退出？
- **面试追问**：`Future.get(timeout)` / `CompletableFuture.orTimeout` / `completeOnTimeout` 三者的区别；为什么 `cancel(true)` 不一定立刻停得掉一个阻塞在 socket 读上的线程。

### 第 3 关 · 单系统故障降级

- **做什么**：让 ERP 报错、HR 卡死，验证只降级这两个、其余照常返回、顺序稳定。
- **要能答**：为什么选"局部降级"而不是"整页失败"？什么业务反而应该整页失败？
- **面试追问**：降级要不要告警？告警指标看什么？

### 第 4 关 ·（进阶）整页时间预算

- **做什么**：把"每个上游各等一次 timeout"改成**统一的 deadline**。
- **要能答**：不做 deadline 时，最坏耗时是多少？（答：上游数量 × timeout，"整页 250ms"就是假的。）

**产出物**：一张能默画出来的调用链 + 上面每个问题的口头答案。练完这一套，简历上"线程池并发聚合"才有画面感。

## 大纲四 · 会议通知：参会人上百人怎么查、怎么发（MySQL 专题）

**业务大概**（面试能这么讲就行）：

- **谁在用**：集团办公室的会议管理员。他在 OA 里建会议、挑议题挂上去，议题上标着「参会部门 / 参会人」。
- **流程**：建一场会 → 从议题库里挑几个议题挂上 → 每个议题带一批参会部门（部门再带出部门负责人）→ 保存会议时，系统把这些部门和人员汇总成一份**参会人名单** → 再按名单逐个下发通知（OA 待办 + 短信）。
- **为什么会有上百人**：一个议题常挂十几个部门，一场会挂 6~10 个议题，部门负责人加参会人员叠起来轻松过百。
- **原来的毛病**：保存会议时「按议题一条条查参会人」，一场会要发几十条 SQL；下发又是 `for` 循环一条条发，一条按 20ms 算，几百人就是十几秒，页面一直转圈。
- **改造后**：参会人查询改成批量查（SQL 条数降下来），通知改成线程池并发下发（几百人几秒发完），单条失败不拖累其它人，失败落表重试。

> 不用跟真实代码一比一，讲得出 **会议 → 议题 → 参会人 → 下发通知** 这条链就够。

### 第 1 关 · 造数与复现

- **做什么**：Docker 起 MySQL 8，建三张表：`meeting`（会议）、`meeting_topic`（议题，带 `status`、`publish_time`）、`topic_attendee`（议题 ↔ 参会人）。造 5 万行议题，一场会议挂 8 个议题、每个议题 10 个参会人。
- **要看到**：拼参会人时 SQL 条数随议题数线性上涨；下发时一串串等着。
- **要能答**：主键单查明明很快，为什么整体还是慢？

### 第 2 关 · 一条 EXPLAIN 看明白

- **做什么**：对「按议题查参会人」那条 SQL 跑 `EXPLAIN`。
- **要能答**：`type` 的档位怎么排；`key` 到底用没上；`rows` 是估算不是精确值；`Extra` 里 `Using filesort` / `Using temporary` / `Using index` 分别什么意思。
- **面试追问**：`rows` 是怎么估出来的？`type=ALL` 和 `type=index` 差在哪？

### 第 3 关 · 索引与批量查询

- **做什么**：`topic_attendee(topic_id)` 原来没索引 → 加上；再把循环里的单查换成 `where topic_id in (…)`，超过 500 就分批。
- **要看到**：`type` 从 `ALL` 变 `ref`、`rows` 掉下来；SQL 条数从几十降到个位数。
- **要能答**：没索引为什么就是全表扫描；`in` 列表太长为什么反而慢。

### 第 4 关 · 上百人并发下发

- **做什么**：300 个通知，串行 mock 20ms/条 ≈ 6 秒；改成手写 `ThreadPoolExecutor`（7 个参数自己定 + 有界队列 + 拒绝策略 + 命名线程工厂）。
- **要能答**：核心线程数怎么定、队列为什么必须有界、四种拒绝策略怎么选、单条失败怎么隔离。
- **面试追问**：`submit` 和 `execute` 抛异常有什么差别？任务抛异常后线程会不会死？

### 第 5 关 · 并发之后看数据库

- **做什么**：并发写推送记录表。
- **要能答**：一条 SQL 一个事务 vs 批量 `insert … values (…),(…)`；行锁等待 / 死锁怎么定位（`show engine innodb status`）；推送日志表该建什么索引。

**交付物与目录（照这个来，不用自己设计）**

- **目录**：`coding-lab/mysql-meeting-lab/`，附 `README.md` 与 `run.sh`（起 MySQL 8 容器 → 建表造数 → 跑串行/并发两版 → 打印对比）。MySQL 用 Docker 起，参考已有的 `coding-lab/mysql-index-lab/docker-compose.yml`。
- **建表**（够用就行，别照抄真实系统）：

  | 表 | 字段 | 造数 |
  |---|---|---|
  | `meeting` | `id, subject, hold_time, status` | 少量 |
  | `meeting_topic` | `id, meeting_id, subject, status, publish_time` | 5 万行 |
  | `topic_attendee` | `id, topic_id, person_id` | 每议题 10 行；**先不建索引** |
  | `push_log` | `id, meeting_id, person_id, status, create_time` | 空表，跑完看写入 |

- **基线 SQL**：循环执行 `select person_id from topic_attendee where topic_id = ?`（一场会议 8 个议题 = 8 次；改成"每个议题再回查一次详情"就变成几十次）。
- **要记录的数字**：保存一次会议的 **SQL 条数** 与 **总耗时**；抓一条 `EXPLAIN` 记下 `type / key / rows`；加索引 + 换 `in` 批量后再记一遍；下发环节记串行总耗时、线程池并发总耗时、拒绝策略触发次数、失败条数。

**验收（跑通什么样算过）**

- 能贴出一份 before / after：SQL 条数从几十 → 个位数；`type` 从 `ALL` → `ref`；`rows` 从 5 万 → 个位数。
- 第 2 关和第 4 关的追问能口头答上来（`EXPLAIN` 各列怎么读 / 线程池 7 参数与拒绝策略）。
- 练习记录写到 `coding-lab/mysql-meeting-lab/练习记录.md`。

**产出物**：一串 `EXPLAIN` 前后对比（`type` / `key` / `rows` / `Extra`），加一张「查参会人 → 拼集合 → 并发下发」的链路图。

## 大纲五 · 议题列表「状态 + 时间」分页：联合索引

**业务大概**（面试能这么讲就行）：

- **谁在用**：各部门在 OA 里提「议题」（拟稿 → 走审批 → 变成「待上会」）；会议管理员在议题管理列表里筛「审批中 / 已上会」，按上会时间倒序翻页，挑议题挂到某场会上；会后议题状态变「已上会」，并和会议纪要关联。
- **数据长相**：议题表是长期堆积的，几万行起步，`status` 只有 3 个取值（草稿 / 审批中 / 已上会），`publish_time` 铺满两年。
- **原来的毛病**：列表一次只显示 20 条，但数据库得先把满足状态的行按时间排好才能取前 20 条；表上只有单列索引（时间一个、创建时间一个），「状态 + 时间」这个组合用不上完整索引，只能扫一大堆再排序 —— 就是 `EXPLAIN` 里的 `rows` 很大 + `Using filesort`。
- **改造后**：建 `(状态, 时间)` 联合索引，等值列在前、排序列在后，`rows` 掉到几十、`filesort` 消失。

> 讲得出 **提议题 → 审批 → 待上会 → 挂到会议 → 已上会** 这条状态流，加上「列表默认只看两个状态、按时间倒序分页」就够了。

### 第 1 关 · 基线与 EXPLAIN

- **做什么**：5 万行议题，`status` 只有 3 个取值，`publish_time` 铺满两年；跑 `where status in ('20','30') order by publish_time desc limit 0,20`。
- **要看到**：慢；`Extra` 里出现 `Using filesort`。
- **要能答**：`Using filesort` 到底是什么（不是"用文件排序"，是额外排序）；为什么单列索引在这里只用到一半。

### 第 2 关 · 联合索引 `(status, publish_time)`

- **做什么**：加索引，同一句 SQL 再跑一次。
- **要看到**：`rows` 从几万掉到几十，`filesort` 消失。
- **要能答**：为什么顺序是「等值列在前、排序列在后」；最左前缀原则怎么解释这次的效果。

### 第 3 关 · 反例：把顺序倒过来

- **做什么**：改成 `(publish_time, status)` 再跑。
- **要能答**：执行计划为什么变了；什么情况下反过来反而更好。

### 第 4 关 · 覆盖索引与深分页

- **做什么**：把列表要显示的列补进索引，看 `Extra=Using index`；再对比 `limit 200000, 20` 与游标分页（`where id > ? limit 20`）。
- **要能答**：回表是什么、什么时候值得做覆盖索引；`offset` 大为什么一定慢；索引多了的代价。

**交付物与目录（照这个来）**

- **目录**：`coding-lab/mysql-index-lab/topic-list/`（直接复用同目录下已有的 MySQL 8 compose，别另起一套）。
- **表**：`meeting_topic(id, subject, status, publish_time, create_time, proposer_dept)`，5 万行；`status` 只给 3 个取值（`10` 草稿 / `20` 审批中 / `30` 已上会），`publish_time` 铺满两年。
- **基线 SQL**：

  ```sql
  select id, subject, status, publish_time
    from meeting_topic
   where status in ('20','30')
   order by publish_time desc
   limit 0, 20;
  ```

- **要跑的四种索引**（每种都记一遍 `EXPLAIN`）：无索引 → 单列 `(publish_time)` → 联合 `(status, publish_time)` → 反例 `(publish_time, status)`；再加一轮覆盖索引 `(status, publish_time, subject)`。
- **要记录的数字**：每次的 `type / possible_keys / key / key_len / rows / filtered / Extra`，加上实际耗时；深分页那关记 `limit 200000,20` 与游标分页的耗时差。

**验收（跑通什么样算过）**

- 有一张至少 5 行的 `EXPLAIN` 对照表（无索引 / 单列 / 联合 / 反例 / 覆盖），能指着表说清每列什么意思、为什么列顺序这么定。
- `filesort` 在加联合索引后消失，`rows` 从几万掉到几十 —— 这个变化要能在输出里指出来。
- 练习记录写到 `coding-lab/mysql-index-lab/topic-list/练习记录.md`。

**产出物**：一张「SQL → EXPLAIN → 加索引 → 再 EXPLAIN」的对照表，能口头从头讲完。

## 顺序建议（只有三个，按这个顺序出）

1. **大纲四（优先）** —— 会议通知：造数 + `EXPLAIN` + 加索引 / 改批量查 + 上百人并发下发。要 Docker 起 MySQL 8。
2. **大纲五** —— 议题列表联合索引：同一个 MySQL 容器就能跑，紧跟着大纲四做，中间不用换环境。
3. **大纲一** —— 统一待办聚合（纯 JDK，不依赖任何中间件），把线程池 7 参数这套地基垫上。

> 大纲四、大纲五 是同一类东西（MySQL 索引 + 执行计划），建议做成**一个工程两个模块**，一次把 MySQL 起起来跑完两份。
