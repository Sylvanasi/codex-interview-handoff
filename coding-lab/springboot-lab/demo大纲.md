# Demo 学习大纲（只有大纲，不落代码）

> 用途：先把"要练什么、每关要能答出什么"定清楚，再动手写代码。
> 两个大纲对应简历上两处最需要补的落点：**JUC 线程池** 和 **Redis 幂等**。
> 版本：v1 · 2026-10-11

## 大纲一 · 统一待办聚合（JUC 线程池）：从串行到并发

**场景锚点（真实的那个）**：集团门户首页要展示 OA / ERP / HR / FIN 四个系统的待办。
原实现是串行调用，光上游就约 470ms，任一系统抖动整页跟着卡。

### 第 0 关 · 热身：先把"_提交任务 → 拿 Future → get 结果_"这条链路跑通

- **做什么**：固定线程池，把 4 个上游并发跑完，打印全部待办和总耗时。
- **验收**：8 条待办齐全，总耗时 < 200ms。
- **要能答**：线程池提交任务后，线程是怎么复用的？为什么不是每个任务 new 一个线程？

### 第 1 关 · 手写 7 个参数

- **做什么**：把 `Executors.newFixedThreadPool(n)` 换成手写 `ThreadPoolExecutor`，7 个参数自己定。
- **要能答**：核心线程数为什么是这个数？队列为什么**必须**有界？拒绝策略选的哪个、什么时候会被触发？
- **面试追问**：执行顺序到底是"核心线程 → 队列 → 非核心线程 → 拒绝"，还是"核心满了就开非核心"？为什么阿里规约禁止用 `Executors`？

### 第 2 关 · 超时控制

- **做什么**：给每个上游加 250ms 超时。
- **要能答**：`get(timeout)` 超时返回之后，那个还在跑的上游任务会不会被中断？进程要多久才能退出？
- **面试追问**：`Future.get(timeout)` / `CompletableFuture.orTimeout` / `completeOnTimeout` 三者的区别；为什么 `cancel(true)` 不一定立刻停得掉一个阻塞在 socket 读上的线程。

### 第 3 关 · 单系统故障降级

- **做什么**：让 ERP 报错、HR 卡死，验证只降级这两个、其余照常返回、顺序稳定。
- **要能答**：为什么选"局部降级"而不是"整页失败"？什么业务反而应该整页失败？
- **面试追问**：降级要不要告警？告警指标看什么？

### 第 4 关 ·（进阶）整页时间预算

- **做什么**：把"每个上游各等一次 timeout"改成**统一的 deadline**。
- **要能答**：不做 deadline 时，最坏耗时是多少？（答：上游数量 × timeout，"整页 250ms"就是假的。）

**产出物**：一张能默画出来的调用链 + 上面每个问题的口头答案。练完这一套，简历上"线程池并发聚合"才有画面感。

## 大纲二 · 跨系统推送幂等（Redis + DB 两层）

**场景锚点（真实的那个）**：OA 审批完成后把合同台账推给金蝶。推送重试、超时重发、用户重复点提交，都会让同一张单进对方系统两次。

### 第 1 关 · 并发窗口

- **做什么**：20 个线程同时推同一张单。先"查一次再写"的写法会推 20 次；换成 `SETNX` 原子占位只推 1 次。
- **要能答**：为什么"先 exists 再 set"等于自己造了一个并发窗口？

### 第 2 关 · 顺序

- **做什么**：对比"先推再记账"和"先占位再推"。
- **要能答**：推成功了但这侧崩了怎么办？明确失败时必须做什么（释放占位），否则会漏推。

### 第 3 关 · 超时

- **做什么**：让对方"处理成功但响应超时"。
- **要能答**：超时是**未知状态**，不是失败状态 —— 直接重试是赌运气，要先查单。

### 第 4 关 · TTL 与最终兜底

- **做什么**：把占位 TTL 调短，让它过期后再重试。
- **要能答**：Redis 会过期、会重启，谁是最后一道防线？（答：数据库唯一索引 / 幂等状态表。）

**产出物**：三句话 —— 幂等键选什么值、顺序怎么定、超时怎么处理。

## 大纲三 · 报销凭证批量归档：SFTP 单通道串行 → 线程池并发

**场景锚点（你自己代码里的）**：罗格朗 OA 费控与 SAP 集成。`SFTPUtil` 是单例，
`connect` / `uploadFile` / `downloadFile` / `listFiles` / `deleteFile` 全部 `synchronized`；
`TclCostVoucherServiceImp.updateVoucherBatchToU(String[] ids)` 也是 `synchronized`。
批量凭证归档时只能一张一张传，耗时随凭证数线性增长。

### 第 1 关 · 先把瓶颈复现出来

- **做什么**：写个循环串行上传 100 个小文件，记总耗时。
- **要看到**：多开几个线程也没用 —— `synchronized` 把入口锁死了，线程全在门外排队。

### 第 2 关 · 把锁找出来，判断粒度对不对

- **要能答**：锁对象是谁？（单例对象 this。）锁的粒度合理吗？（不合理：把"连接管理"和"文件传输"一把锁锁在一起了。）
- **面试追问**：`synchronized` 修饰实例方法和修饰静态方法，锁的对象分别是什么？

### 第 3 关 · 拆锁 + 并发上传

- **做什么**：SFTP 连接改成**每线程一个**（或连接池），上传动作丢进 `ThreadPoolExecutor`。
- **要能看到**：100 个文件的总耗时接近原来的 1/N。
- **要能答**：为什么不能简单地"去掉 synchronized"了事？（因为 `Session` / `ChannelSftp` 本身不是线程安全的，共享会串包、报错。）

### 第 4 关 · 失败隔离

- **做什么**：单个文件失败不能拖垮整批 —— 重试有限次 + 落失败清单 + 告警。
- **要能答**：重试几次？重试还失败呢？（转人工 / 补偿任务，跟大纲二的思路一样。）

### 第 5 关 · 并发带出来的新问题

- **要能答**：SFTP 服务器连接数上限、对方有没有限流、批量任务的成功率怎么观测。

**产出物**：能讲清"锁在哪 → 为什么粒度不对 → 怎么拆 → 拆完新增什么问题"这条完整链路。
