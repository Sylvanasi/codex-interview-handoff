## 大纲四 · 会议通知：参会人上百人怎么查、怎么发（MySQL 专题）

**业务大概**（面试能这么讲就行）：

- **谁在用**：集团办公室的会议管理员。他在 OA 里建会议、挑议题挂上去，议题上标着「参会部门 / 参会人」。
- **流程**：建一场会 → 从议题库里挑几个议题挂上 → 每个议题带一批参会部门（部门再带出部门负责人）→ 保存会议时，系统把这些部门和人员汇总成一份**参会人名单** → 再按名单逐个下发通知（OA 待办 + 短信）。
- **为什么会有上百人**：一个议题常挂十几个部门，一场会挂 6~10 个议题，部门负责人加参会人员叠起来轻松过百。
- **原来的毛病**：保存会议时「按议题一条条查参会人」，一场会要发几十条 SQL；下发又是 `for` 循环一条条发，一条按 20ms 算，几百人就是十几秒，页面一直转圈。
- **改造后**：参会人查询改成批量查（SQL 条数降下来），通知改成线程池并发下发（几百人几秒发完），单条失败不拖累其它人，失败落表重试。

> 不用跟真实代码一比一，讲得出 **会议 → 议题 → 参会人 → 下发通知** 这条链就够。

### 第 1 关 · 造数与复现

- **做什么**：Docker 起 MySQL 8，建三张表：`meeting`（会议）、`meeting_topic`（议题，带 `status`、`publish_time`）、`topic_attendee`（议题 ↔ 参会人）。造 5 万行议题，一场会议挂 8 个议题、每个议题 10 个参会人。
- **要看到**：拼参会人时 SQL 条数随议题数线性上涨；下发时一串串等着。
- **要能答**：主键单查明明很快，为什么整体还是慢？

### 第 2 关 · 一条 EXPLAIN 看明白

- **做什么**：对「按议题查参会人」那条 SQL 跑 `EXPLAIN`。
- **要能答**：`type` 的档位怎么排；`key` 到底用没上；`rows` 是估算不是精确值；`Extra` 里 `Using filesort` / `Using temporary` / `Using index` 分别什么意思。
- **面试追问**：`rows` 是怎么估出来的？`type=ALL` 和 `type=index` 差在哪？

### 第 3 关 · 索引与批量查询

- **做什么**：`topic_attendee(topic_id)` 原来没索引 → 加上；再把循环里的单查换成 `where topic_id in (…)`，超过 500 就分批。
- **要看到**：`type` 从 `ALL` 变 `ref`、`rows` 掉下来；SQL 条数从几十降到个位数。
- **要能答**：没索引为什么就是全表扫描；`in` 列表太长为什么反而慢。

### 第 4 关 · 上百人并发下发

- **做什么**：300 个通知，串行 mock 20ms/条 ≈ 6 秒；改成手写 `ThreadPoolExecutor`（7 个参数自己定 + 有界队列 + 拒绝策略 + 命名线程工厂）。
- **要能答**：核心线程数怎么定、队列为什么必须有界、四种拒绝策略怎么选、单条失败怎么隔离。
- **面试追问**：`submit` 和 `execute` 抛异常有什么差别？任务抛异常后线程会不会死？

### 第 5 关 · 并发之后看数据库

- **做什么**：并发写推送记录表。
- **要能答**：一条 SQL 一个事务 vs 批量 `insert … values (…),(…)`；行锁等待 / 死锁怎么定位（`show engine innodb status`）；推送日志表该建什么索引。

- **建表**（够用就行，别照抄真实系统）：

  | 表 | 字段 | 造数 |
  |---|---|---|
