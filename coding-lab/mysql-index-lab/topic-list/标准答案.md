# 标准答案（练习后查看）

关键SQL见01～04编号文件；以下解释对应每关四个追问。

## 第1关

1. 没有可用有序索引，先扫描过滤，再排序，LIMIT只限制最终结果。
2. EXPLAIN的rows来自统计估算，COUNT是真实计数；结合ANALYZE实际节点判断。
3. filesort是额外排序算法，可能在内存完成，也可能使用磁盘。
4. 默认RR/RC下普通一致性SELECT通常不加记录锁，不能与FOR UPDATE混淆；仍涉及元数据锁等机制。

## 第2关

1. `(status,publish_time,id)`按状态分组；status固定后，后两列连续有序。
2. 全ASC索引可向后扫描满足两个DESC排序列。
3. 估算rows可能表示整个状态范围，LIMIT可提前停止；实际节点读取20条，不应把估算硬要求为20。
4. subject不在该索引内，读取它需回聚簇索引；InnoDB二级索引带主键，显式列出id是为了直观说明排序。

## 第3关

1. 状态20和30各自时间有序，两段拼起来不保证跨状态时间有序，需要额外排序或其他策略。
2. possible_keys是候选，优化器比较成本后可能选择全表扫描。本数据约2/3命中，回表和排序成本较高。
3. 时间优先可有序扫描到20条就停，但状态作为后续过滤；若命中稀少，可能扫描很多条。
4. 用不同分布重跑ANALYZE与EXPLAIN ANALYZE，比较实际扫描量和多轮耗时，不能只背最左原则。

## 第4关

1. Using index表示覆盖；Using index condition表示索引条件下推，仍可能回表。
2. 二级索引叶子保存主键用于定位聚簇记录。
3. 不合理，宽字段/过多索引增加空间与写维护成本，应围绕高频查询选择。
4. 插入、更新、删除需要维护索引，增加日志、页操作和存储成本。

## 第5关

下一页的核心条件（倒序）：

```sql
WHERE status='20'
  AND (publish_time < @cursor_time
       OR (publish_time = @cursor_time AND id < @cursor_id))
ORDER BY publish_time DESC,id DESC
LIMIT 20;
```

1. 当前排序按时间+ID，不是按ID；仅id条件会改变分页语义。
2. ID作唯一且稳定的次排序键；游标携带两列，使用严格小于。
3. 通常不支持直接随机跳页，需要已有游标或额外定位机制。
4. 多次HTTP查询不是天然同一快照，期间修改排序键可能漏/重；需明确一致性要求，可选固定水位/快照方案，不能承诺游标解决全部问题。
