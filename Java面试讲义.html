第 1 章HashMap 与 ConcurrentHashMap

这一章几乎是每场面试的开场题。面试官真正想确认的是三件事：你知不知道结构怎么变（链表→红黑树）、扩容怎么算（为什么是 2 倍）、并发下会出什么问题（以及 CHM 怎么修的）。

1.1 底层结构：数组 + 链表 + 红黑树

JDK8 的 HashMap 本质是一个散列表：一个 Node[] 数组，每个下标叫一个「桶」，哈希冲突的元素挂在同一个桶里，先用链表串起来，链表太长就转成红黑树。

常量值为什么是这个值
DEFAULT_INITIAL_CAPACITY162 的幂，太小频繁扩容，太大浪费空间
DEFAULT_LOAD_FACTOR0.75源码注释：节点近似泊松分布，λ=0.5 时冲突最少；0.75 是空间与冲突概率的折中
TREEIFY_THRESHOLD8负载因子 0.75 下，一个桶里放 8 个元素的概率约 6×10⁻⁸，属于极端情况
UNTREEIFY_THRESHOLD6留 2 的缓冲，避免在 8 附近反复树化/退化抖动
MIN_TREEIFY_CAPACITY64数组太小说明是扩容没跟上，先扩容而不是树化

1.2 hash 扰动：为什么要 h ^ (h >>> 16)

// JDK8 的扰动函数
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

核心矛盾：定位下标用的是 (n-1) & hash，而 n 很小时只有 hash 的低几位参与运算，高位信息被完全浪费。如果两个 key 的 hashCode 只有高位不同、低位相同，它们就会撞到同一个桶。

解决办法就是让高 16 位异或到低 16 位，一次运算就把高低位的信息混合起来，成本极低但显著降低碰撞。

为什么定位能用位运算？因为容量 n 是 2 的幂，此时 (n-1) & hash 与 hash % n 结果完全一致，但位运算比取模快得多。这也反过来解释了「容量为什么必须是 2 的幂」。

1.3 put 全流程

这张图要回答一个很容易被忽略的问题：「key 相同就覆盖」的判定发生在桶里的每一个节点上，而不只是首节点。首节点只是遍历的起点。

这张图最容易看错的地方：「key 相同就覆盖」不是只在首节点判断一次。桶非空时会顺着 next 逐个比较，命中哪个节点就覆盖哪个节点的 value，一路比到尾都没命中，才尾插新节点。首节点只是循环的第一次迭代。
口述模板：先算扰动 hash，用 (n-1)&hash 定位桶；桶为空就直接放；非空先看是不是红黑树，是就交给 putTreeVal；否则从首节点开始顺着链表逐个比 hash 和 equals，命中哪个节点就覆盖哪个；一路比到尾都没命中才尾插；尾插后判断要不要树化；最后 size 超过阈值就扩容。

1.4 扩容：为什么是 2 倍，JDK8 又优化了什么

触发条件：插入新节点后 ++size > threshold，其中 threshold = capacity × loadFactor。

JDK7 扩容要重新计算每个元素的 hash 和下标，代价很大。JDK8 抓住了一个数学性质：容量翻倍后，新的下标只有两种可能。

关键就一句：判断 hash & oldCap 这一位是 0 还是 1。

为什么容量必须是 2 的幂？三个理由串起来答：① (n-1)&hash 才能等价取模；② 位运算比取模快；③ 扩容时元素要么原位要么 +oldCap，不用重算 hash，这是 JDK8 扩容优化的前提。

1.5 树化与退化

  • 树化：链表长度 ≥ 8 且 table.length ≥ 64 → 转红黑树，查询从 O(n) 降到 O(log n)。
  • 退化：扩容后树节点数 ≤ 6 → 退回链表。
  • 数组长度 < 64 时即使链表到 8 也先扩容，因为扩容能立刻把链表拆短，比树化更划算。

1.6 HashMap 为什么线程不安全

版本插入方式并发后果
JDK7头插法并发扩容时链表指针错乱形成环形链表，之后 get 会死循环、CPU 打满
JDK8尾插法不再成环，但两个线程同时 put 可能互相覆盖丢数据，size 也不准
有个细节值得说：JDK8 改成尾插不是为了修死循环，主要是为了配合红黑树转换（需要知道尾节点）。死循环是顺带被修掉的，真正的并发安全仍然要靠 ConcurrentHashMap。

1.7 ConcurrentHashMap：从分段锁到 CAS + synchronized

JDK8 的 put 逻辑（口述重点）

  1. 桶为空：用 CAS 直接放入头节点（失败就重试）。
  2. 桶为 MOVED（ForwardingNode）：说明正在扩容，当前线程去帮忙扩容。
  3. 桶非空：synchronized 锁住头节点，再按链表/红黑树插入。
  4. 插入后 addCount 统计并判断是否触发扩容。

size 的统计：baseCount + CounterCell[]

多个线程同时 ++size 会激烈竞争同一个变量。CHM 借鉴 LongAdder 的分治思想：以 baseCount 为基准，竞争激烈时分散到 CounterCell[] 数组的不同槽，最后累加求和。代价是 size() 只是近似值（弱一致）。

扩容：多线程协助

用 sizeCtl 同时表达「扩容阈值」和「扩容状态」。已迁移的桶放一个 ForwardingNode 占位，其他线程看到它就一起来搬数据，把一次大扩容的工作量分摊给多个线程。

为什么不允许 null

并发场景下，get 返回 null 有两种可能：key 不存在，或者 value 就是 null。单线程的 HashMap 可以用 containsKey 二次确认，但在并发下这中间状态可能已被改写，无法给出确定语义，所以直接禁止。

1.8 高频追问速答

Q：HashMap 为什么线程不安全？
A：JDK7 并发扩容头插会形成环形链表导致 get 死循环；JDK8 改尾插不成环了，但并发 put 仍会覆盖丢数据、size 不准。所以并发场景要用 CHM。
Q：为什么链表长度是 8 才转红黑树？
A：0.75 负载因子下节点数服从泊松分布，一个桶里达到 8 个元素的概率约 6×10⁻⁸，几乎不可能。所以 8 是「正常情况下永远用不到」的兜底阈值，只有恶意构造哈希碰撞才会触发。
Q：ConcurrentHashMap 的 get 需要加锁吗？
A：不需要。Node 的 val 和 next 都是 volatile 的，get 靠可见性保证读到最新值，是无锁读。
Q：为什么 CHM 不允许 null，而 HashMap 可以？
A：CHM 是并发容器，返回 null 无法区分「不存在」和「值为 null」，语义有歧义，所以直接禁止。
Q：CHM 的 size() 是准确的吗？
A：不是。用 baseCount + CounterCell 分散计数，求和得到的是近似值，属于弱一致。并发下想要精确数量，得用 mappingCount() 并接受近似语义。

第 2 章JVM 内存模型与垃圾回收

JVM 这一章面试官最爱问的是：内存区域怎么划、对象怎么分配、垃圾怎么回收、线上出问题怎么查。前三个是八股，最后一个才是分水岭。

2.1 运行时数据区

区域线程存放内容异常
程序计数器私有当前字节码行号唯一不会 OOM
虚拟机栈私有栈帧（局部变量等）StackOverflowError / OOM
本地方法栈私有native 方法同上
堆共享对象实例、数组OOM: Java heap space
方法区 / 元空间共享类元信息、常量、静态变量OOM: Metaspace
直接内存共享NIO 堆外缓冲区OOM: Direct buffer memory
常考细节：JDK8 用元空间（本地内存）取代了 JDK7 的永久代。所以「JDK8 之后 PermGen 去哪了」的答案是：移到本地内存，参数从 -XX:MaxPermSize 变成 -XX:MaxMetaspaceSize。

2.2 对象是怎么创建和分配的

TLAB 是什么？Thread Local Allocation Buffer，每个线程在 Eden 里预先划走一小块私有区域。对象优先在自己的 TLAB 里分配，不需要加锁；TLAB 用完了才走 CAS 向 Eden 申请新的，这样大幅减少指针碰撞的竞争。

2.3 怎么判断一个对象该回收了

主流 JVM 都不用引用计数（循环引用无法回收），而是用 可达性分析：从一组叫 GC Roots 的根对象出发，能走到的对象存活，走不到的就是垃圾。

GC Roots 常见有：虚拟机栈中局部变量表引用的对象、方法区中静态变量引用的对象、常量引用的对象、本地方法栈 JNI 引用的对象、活跃线程、同步锁持有的对象。

引用类型回收时机典型用途
强引用 new永远不会被回收（除非不可达）普通对象
软引用 SoftReference内存不足时才回收缓存
弱引用 WeakReference下次 GC 一定回收ThreadLocal 的 key、WeakHashMap
虚引用 PhantomReference随时可能被回收，只用于回收通知管理直接内存

2.6 类加载机制

加载的五个阶段

加载 → 验证 → 准备 → 解析 → 初始化

  • 准备：为静态变量分配内存并赋零值（static int a = 10 此时 a 是 0，不是 10）。
  • 解析：把常量池的符号引用替换为直接引用。
  • 初始化：执行 <clinit>，此时才真正赋值 10。父类先于子类，多个线程访问时加锁保证只执行一次。
「打破双亲委派」怎么答才不掉分？标准套路是：双亲委派要求向上，但 SPI 机制（比如 JDBC 的 Driver）要求父加载器去调用子加载器加载的实现类，方向反了。解决办法是 Thread.currentThread().getContextClassLoader() 拿到线程上下文类加载器，用它来加载。Tomcat 则是为了应用隔离，让每个 webapp 有自己的 ClassLoader，优先加载自己的类。

2.8 高频追问速答

Q：Minor GC / Major GC / Full GC 区别？
A：Minor GC 只回收新生代（频繁、快）；Major/Old GC 回收老年代；Full GC 回收整个堆（含元空间、直接内存），STW 时间长，要尽量避免。
Q：什么情况下对象直接进老年代？
A：三种 —— 大对象超过阈值、Survivor 空间不足时的分配担保、动态年龄判定（Survivor 中相同年龄对象总和超过一半）。
Q：CMS 为什么不用标记-整理？
A：整理需要移动对象，必须 STW，就达不到「低停顿」这个设计目标了。代价就是碎片。
Q：G1 和 CMS 的本质区别？
A：CMS 按物理分代回收，G1 按 Region 逻辑分代，可以按回收收益排序、设置停顿目标，且用整体整理 + 局部复制避免了碎片问题。
Q：怎么排查内存泄漏？
A：-XX:+HeapDumpOnOutOfMemoryError 拿到 dump，用 MAT 打开，看 Dominator Tree / Leak Suspects，定位到「谁持有大对象的引用链」；在线可以用 Arthas 的 heapdump 或 vmtool 直接取。

第 3 章JUC 并发工具

JUC 的题有个特点：答对概念不难，答出「为什么这么设计」才加分。这一章的主线是 AQS —— 把 AQS 讲清楚，ReentrantLock、Semaphore、CountDownLatch 全都是同一套逻辑的变体。

3.1 AQS：整个 JUC 的地基

一句话定义：AQS（AbstractQueuedSynchronizer）= 一个 volatile 的 state + 一个 FIFO 双向等待队列。抢资源就是改 state，抢不到就排队等待。

自己写一个锁，只要实现两个方法

  • 继承 AbstractQueuedSynchronizer，实现 tryAcquire(int) 和 tryRelease(int)。
  • tryAcquire 里用 compareAndSetState(0, 1) 抢资源，成功设置 setExclusiveOwnerThread 并返回 true，失败返回 false。
  • tryRelease 里清空持有线程并 setState(0)，返回 true。
  • 对外暴露 lock() 调 acquire(1)，unlock() 调 release(1) —— 这两个是 final 模板方法，入队、park、唤醒全都由 AQS 兜底。

独占 vs 共享

模式state 语义代表实现
独占0 空闲，>0 表示被当前线程重入了几次ReentrantLock、ReadWriteLock 的写锁
共享表示可用许可数量，获取时递减Semaphore、CountDownLatch、ReadWriteLock 的读锁

3.2 synchronized 与锁升级

对比项synchronizedReentrantLock

3.3 CAS：无锁的基石

CAS（Compare And Swap）的思想是：「我认为现在应该是 A，如果是，就改成 B」。比较和交换是一步原子操作，由 CPU 指令保证。Java 里通过 Unsafe.compareAndSwapInt 暴露出来。

问题说明解法
ABA 问题值从 A 改成 B 又改回 A，CAS 察觉不到中间的变化加版本号：AtomicStampedReference
自旋开销长时间抢不到会一直空转，浪费 CPU用 LongAdder 分散热点，或退化成锁
只能保证一个变量无法原子地更新多个变量封装成对象用 AtomicReference
面试延伸：为什么 JDK8 还要引入 LongAdder？因为高并发下所有线程 CAS 同一个 value，失败重试极多；LongAdder 把值分散到多个 Cell，各线程各改各的，只有求和时才汇总。

3.4 并发工具：三个最容易混的类

一句话区分：CountDownLatch 是「等人到齐再开始，等一次就废」；CyclicBarrier 是「大家互相等，到齐了一起走，还能再来一轮」。

工具作用可重用典型场景
CountDownLatch一个线程等 N 个线程完成否接口聚合、多任务汇总后计算
CyclicBarrierN 个线程互相等待到齐是分阶段计算、压测起点对齐
Semaphore控制同时访问的线程数量是限流、资源池
Exchanger两个线程交换数据是遗传算法、流水线
Phaser更灵活的多阶段同步是复杂分阶段任务

3.5 ThreadLocal 与内存泄漏

为什么 key 用弱引用？这是一种兜底设计：如果 key 是强引用，只要 Thread 活着，ThreadLocal 对象就永远回收不掉，泄漏会变成必然。用弱引用后，至少外部没有引用时 key 能被回收。但 value 的回收只能靠 remove()。

3.7 高频追问速答

Q：AQS 为什么用双向队列而不是单向？
A：需要支持从中间取消。线程等待超时或被打断时要从队列中摘掉自己，双向链表才能 O(1) 找到前驱。
Q：ReentrantLock 默认公平还是非公平？为什么？
A：非公平。非公平锁允许刚到的线程直接尝试抢锁，省掉一次线程唤醒的上下文切换，吞吐量更高；代价是可能出现饥饿。
Q：synchronized 和 volatile 的区别？
A：volatile 只保证可见性和有序性，不保证原子性；synchronized 三者都保证。volatile 靠内存屏障实现，开销比锁小得多。
Q：ThreadLocal 会传给子线程吗？
A：不会。InheritableThreadLocal 会在创建子线程时把父线程的值复制一份过去，但它是拷贝，父子线程后续修改互不影响。线程池里因为线程复用，用它会串数据。
Q：为什么 CopyOnWriteArrayList 读快写慢？
A：读没有任何锁和同步，直接读数组；写要整体复制一份数组（O(n)）再替换 volatile 引用，内存占用瞬时翻倍。所以只适合读多写极少的场景。

第 4 章线程池

线程池是极少数「既能问原理、又能问实战」的知识点。面试官通常从「七个参数」切入，再用「为什么不用 Executors」和「参数怎么定」来判断你有没有真正在生产环境用过。

4.1 为什么要用线程池

  • 降低资源消耗：线程的创建和销毁都有成本，复用线程避免频繁开销。
  • 提高响应速度：任务到达时线程已经存在，可以直接执行。
  • 提高可管理性：可以统一控制并发数、排队策略、监控与调优。

参数含义注意点
corePoolSize核心线程数默认即使空闲也常驻（除非开启 allowCoreThreadTimeOut）
maximumPoolSize最大线程数核心 + 非核心的总上限
keepAliveTime非核心线程空闲存活时间超时后被回收
unit时间单位配合 keepAliveTime
workQueue任务队列选无界队列会让 maximumPoolSize 失效
threadFactory线程工厂生产必改，起有意义的线程名便于排查
handler拒绝策略默认抛异常，生产多为自定义

4.3 执行流程：这是本章最该背下来的一张图

口述模板：核心线程没满就开核心线程；核心满了先丢进队列；队列满了才开非核心线程；非核心也到上限就执行拒绝策略。

补充两个容易漏的细节

  • 入队成功后会 double-check：如果线程池已经 STOP，就把任务从队列移除并拒绝；如果这时 worker 数为 0（可能上一个线程刚销毁），会补建一个线程。
  • 非核心线程空闲超过 keepAliveTime 会被回收；核心线程默认不回收，除非设置 allowCoreThreadTimeOut(true)。

4.4 四种拒绝策略

策略行为适用场景
AbortPolicy（默认）直接抛 RejectedExecutionException需要感知失败并快速失败
CallerRunsPolicy交给提交任务的线程自己执行给上游施加背压，不丢任务；适合任务不能丢的场景
DiscardPolicy静默丢弃，什么都不做允许丢任务，但无法感知，一般不推荐
DiscardOldestPolicy丢掉队首最老的任务，再尝试提交当前任务只关心最新数据，如实时上报
生产建议：用 自定义拒绝策略：既记录日志/埋点，又按业务决定是抛异常、降级还是落库重试。单纯的 DiscardPolicy 会让故障「静默发生」，排查时毫无线索。

4.5 线程池的状态流转

4.6 队列怎么选

队列是否有界行为
ArrayBlockingQueue有界必须指定容量，最可控，生产推荐
LinkedBlockingQueue默认近似无界maximumPoolSize 会形同虚设，任务无限积压到 OOM
SynchronousQueue不存储任务直接交给线程，没有线程就创建，配合大 maximumPoolSize
PriorityBlockingQueue无界按优先级执行，注意同样有积压风险
DelayQueue无界延时任务
关键因果关系：队列选无界 → 永远不会触发「队列满」，所以永远不会创建非核心线程，maximumPoolSize 完全失效，任务一路堆到内存耗尽。这就是 FixedThreadPool 的隐患来源。

4.7 参数怎么定

任务类型推荐线程数理由
CPU 密集型N + 1线程多了只会增加上下文切换，+1 用于应对偶发缺页
IO 密集型2N 或更高线程大部分时间在等待，留出并行度
精确估算N × (1 + 等待时间 / 计算时间)等待占比越高，线程数应越大

（N 为 CPU 核心数，用 Runtime.getRuntime().availableProcessors() 获取。）

实践中的四条经验：

  • 核心数和非核心数设成一样，避免线程频繁创建销毁带来的抖动。
  • 用有界队列 + 明确的拒绝策略，让问题尽早暴露而不是拖到 OOM。
  • 不同业务用不同的线程池隔离，别用一个池子跑所有任务（一个慢业务会拖垮全部）。
  • 用自定义 ThreadFactory 给线程起业务可辨识的名字，出问题时 jstack 一眼能认出来。

4.8 为什么不用 Executors 创建线程池

快捷方法隐患
newFixedThreadPool用 无界 LinkedBlockingQueue，任务无限堆积 → OOM
newSingleThreadExecutor同上，无界队列
newCachedThreadPoolmaximumPoolSize = Integer.MAX_VALUE，用 SynchronousQueue，任务激增时无限创建线程 → OOM，甚至打挂系统
newScheduledThreadPoolmaximumPoolSize 同样是 Integer.MAX_VALUE
标准答法：《阿里巴巴 Java 开发手册》明确要求不允许用 Executors 创建线程池，因为这些快捷方法要么用无界队列导致任务堆积 OOM，要么最大线程数是 Integer.MAX_VALUE 导致无限创建线程。正确做法是手动 new ThreadPoolExecutor(...)，明确指定有界队列、线程工厂和拒绝策略。

4.9 生产实践：监控与动态调参

  • 监控指标：getActiveCount()（活跃线程数）、getQueue().size()（队列积压）、getCompletedTaskCount()（完成数）、最大线程数、拒绝次数。
  • 动态调参：setCorePoolSize / setMaximumPoolSize 可以运行时修改；美团开源的 DynamicTp、配置中心推送是常见方案。
  • 线程池隔离：不同业务、不同优先级的任务分开池子，避免相互影响。
  • 队列积压告警：队列长度持续增长通常意味着下游变慢或线程数不足，比等待 OOM 更早暴露问题。

4.10 高频追问速答

Q：核心线程会一直存活吗？
A：默认是。但可以调用 allowCoreThreadTimeOut(true)，让核心线程也享受 keepAliveTime 超时回收，适合流量波峰波谷明显的场景。
Q：线程池里的线程抛异常了会怎样？
A：用 execute() 提交时，异常会打印到控制台并杀掉这个线程，线程池会再补一个新线程；用 submit() 提交时异常被包进 Future，不调用 get() 就永远看不到。所以要么 execute + try-catch，要么 submit + get，要么在 ThreadFactory 里设置 UncaughtExceptionHandler。
Q：线程池在什么时机创建线程？
A：默认是任务提交时惰性创建。想要预热可以用 prestartAllCoreThreads() 或 prestartCoreThread()。
Q：怎么优雅关闭线程池？
A：先 shutdown() 停止接收新任务，再 awaitTermination(timeout) 等待已有任务执行完；超时后视情况 shutdownNow() 强制中断。顺序不能反，否则会丢任务。
Q：怎么判断线程池该扩还是该缩？
A：看队列。如果队列经常积压但线程数没到上限，说明队列太深或 maximumPoolSize 太小；如果队列一直空但线程数很高，说明线程开多了，可以降低。

第 5 章Redis

Redis 的面试基本遵循一条主线：为什么快 → 怎么不丢数据 → 缓存怎么不出事 → 分布式锁怎么写。前两个是原理，后两个是实战，而且几乎一定会追问到你的项目。

5.1 为什么 Redis 这么快

「单线程」到底指什么？指执行命令的那段逻辑是单线程的。所以不用加锁、不会出现并发写同一份数据的问题。但 Redis 并不是真的只有一个线程 —— 它还有后台线程处理持久化（BGSAVE/BGREWRITEAOF）、异步删除（unlink）等工作。

5.2 数据类型与底层编码

类型说明底层编码典型场景
String二进制安全，最大 512MBint / embstr / raw（SDS）缓存对象、计数器、分布式锁
Hash字段级读写listpack / hashtable存对象、购物车
List双向链表，支持两端操作quicklist（listpack 组成的双向链表）消息队列、最新列表
Set无序不重复intset / listpack / hashtable去重、共同好友
ZSet有序不重复，按 score 排序listpack / skiplist + hashtable排行榜、延时队列
Bitmap位操作String签到、布隆过滤器
HyperLogLog基数统计，误差 0.81%稀疏/稠密编码UV 统计
Geo地理位置ZSet（geohash）附近的人
Stream消息流，支持消费组radix tree消息队列
ZSet 为什么用跳表而不是红黑树？三个理由：① 跳表实现更简单，代码量小、易于维护和调试；② 范围查询更自然（ZRANGE 顺着底层链表走即可），红黑树需要中序遍历；③ 并发友好，局部修改只影响相邻节点。代价是空间复杂度略高（多级索引）。

5.3 持久化：RDB 与 AOF

RDBAOF
内容某一时刻的数据快照（二进制）记录所有写命令
文件大小小，压缩存储大，可重写压缩
恢复速度快慢，要重放命令
数据安全可能丢失最后一次快照之后的数据取决于 appendfsync 策略
fork 开销BGSAVE 时 fork 子进程，写时复制AOF 重写同样需要 fork
触发方式save / bgsave / 自动（如 900 秒内 1 次修改）appendonly yes

AOF 的三档刷盘策略（对应 appendfsync）：

  • always：每条命令都 fsync，最安全但性能最差。
  • everysec（默认）：每秒 fsync 一次，最多丢 1 秒数据，性能与安全的平衡点。
  • no：交给操作系统决定何时刷盘，最快但可能丢较多数据。
混合持久化（Redis 4.0+，推荐）：AOF 重写时，先以 RDB 格式写入当前全量数据，之后的增量命令继续以 AOF 格式追加。这样既有 RDB 的快速恢复，又有 AOF 的低数据丢失风险。

5.4 过期删除与内存淘汰

过期删除策略是两者的组合：

  • 惰性删除：访问 key 时才检查是否过期，过期就删。省 CPU，但过期 key 可能长期占内存。
  • 定期删除：每秒随机抽查一部分设置了过期时间的 key，删除其中已过期的。是「抽样」而不是全量扫描，避免阻塞。

内存淘汰策略（maxmemory-policy）：

策略含义
noeviction不淘汰，写入直接报错（默认）
allkeys-lru所有 key 中淘汰最久未使用的，最常用
allkeys-lfu所有 key 中淘汰访问频率最低的（Redis 4.0+）
volatile-lru / lfu只在设置了过期时间的 key 中淘汰
volatile-ttl优先淘汰即将过期的 key
allkeys-random / volatile-random随机淘汰
LRU vs LFU：LRU 只看「最近是否用过」，一个很久没访问但突然被大量访问的 key 容易被误删；LFU 看「访问频率」，更能保护真正的热 key。热点数据明显的业务优先用 LFU。

5.5 三大缓存问题

问题一句话本质解决方案
穿透数据根本不存在，缓存无从命中布隆过滤器拦截、缓存空值并设短过期时间、参数校验
击穿单个热点 key 失效瞬间并发涌入互斥锁（只放一个线程去查 DB，其他等待）、逻辑过期（不设 TTL，异步更新）
雪崩大量 key 同时失效或 Redis 整体不可用过期时间加随机值、集群高可用、多级缓存、服务熔断降级、提前预热
三个问题的记忆锚点：穿透 = 「查无此物」；击穿 = 「一个点被打穿」；雪崩 = 「整座山塌了」。

5.6 缓存与数据库的一致性

面试怎么说才显专业：先给结论 —— 缓存和数据库无法做到强一致，只能做到最终一致。标准方案是 Cache Aside（先更新库、再删缓存），因为删除比更新更不容易产生脏数据；如果业务对一致性要求更高，再上延迟双删或binlog 订阅，同时用「过期时间 + 异步补偿」兜底。

5.7 分布式锁

为什么这几个要素都不能少

要素缺失的后果
NX（不存在才设置）锁会被后者直接覆盖，完全失去互斥性
PX / EX（过期时间）持锁方宕机，锁永远不释放，形成死锁
unique value（唯一值，如 UUID + 线程 ID）无法区分锁是谁加的，会误删他人的锁

两个高频追问：
① 锁过期了业务还没执行完怎么办？—— 用 Redisson 的看门狗自动续期；简单实现则把过期时间设得足够长并加业务超时。
② 主从架构下锁可靠吗？—— 不可靠。主节点写入后还未同步给从节点就宕机，从节点升主后锁就丢了。这就是 RedLock 想解决的问题（向多数节点加锁），但 RedLock 本身也有争议。真正要求强一致的场景，建议用 ZooKeeper / etcd：它们基于 ZAB / Raft，保证写入已提交后才返回。

5.8 高可用：主从、哨兵、集群

方案解决的问题局限
主从复制读扩展、数据备份主挂了需要人工切换
哨兵 Sentinel监控 + 自动故障转移 + 通知客户端新主仍是单主，写能力和容量受单机限制
Cluster 集群数据分片（16384 个 slot）+ 高可用运维复杂，跨 slot 的多 key 操作受限
复制原理：从节点首次连接主节点时发起 全量同步（主节点 fork 生成 RDB + 缓冲区内的增量命令）；之后的 增量同步靠 repl_backlog 环形缓冲区完成。主从复制默认是异步的，所以会有一致性窗口。

5.9 高频追问速答

Q：Redis 是单线程，为什么还这么快？
A：纯内存操作、IO 多路复用、高效数据结构，再加上单线程避免了锁竞争和上下文切换。
Q：big key 有什么危害？
A：单线程模型下，一个 big key 的读取/删除会阻塞整个实例；网络传输也会瞬间打满带宽。要拆分成多个小 key，删除用 unlink 异步删除。
Q：怎么实现延时队列？
A：用 ZSet，score 存执行时间戳，起一个线程轮询 ZRANGEBYSCORE 0 当前时间，到点的取出来执行并删除；或者直接用 Redisson 的 RDelayedQueue。
Q：如何用 Redis 实现限流？
A：固定窗口用 INCR + EXPIRE；滑动窗口用 ZSet（存请求时间戳，统计窗口内的数量）；最精确的是令牌桶，用 Lua 脚本保证「取令牌 + 放令牌」的原子性。
Q：pipeline 和 Lua 的区别？
A：pipeline 只是把多条命令批量发送，减少网络往返，但不保证原子性；Lua 脚本在服务端整体原子执行，中间不会插入其他命令。
Q：缓存和数据库双写，先删缓存还是先更新库？
A：推荐先更新数据库、再删除缓存。反过来的话，在删除缓存和更新数据库之间如果有一个读请求进来，会把旧值重新加载进缓存，导致长期脏数据；而「先更新库后删缓存」的脏窗口极短，且可用延迟双删兜底。

第 6 章分布式事务

这一章的答题结构很固定：先说为什么单机事务不够用 → 再说理论（CAP / BASE）→ 最后按方案分类展开。面试官最想听到的是「为什么这个业务场景选这个方案」，所以每个方案都要记住它的代价。

6.1 为什么单机事务不够用了

本地事务（ACID）依赖数据库的锁和日志，前提是所有操作在同一个数据库连接、同一个资源管理器里。一旦业务被拆成多个服务、每个服务用各自的数据源，本地事务就无能为力了。

典型场景：下单要同时做「订单库创建订单」和「库存库扣减库存」，两个库在两个服务里，没法用一个 @Transactional 搞定。

6.2 理论基础

理论含义
CAP一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可同时满足。分布式系统必然存在网络分区，所以 P 必须保留，实际是在 C 和 A 之间取舍。
BASEBasically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致）。是 CAP 中放弃强一致、保留可用性的实践路线。
一句话说透：金融核心（转账、支付记账）倾向 CP，宁可失败也不能算错；电商、社交这类业务倾向 AP，接受短暂不一致，靠补偿达到最终一致。绝大多数互联网分布式事务方案走的都是 BASE 路线。

6.3 两阶段提交（2PC / 3PC）

XA 与 2PC 的关系：XA 是 X/Open 组织定义的分布式事务规范，2PC 是它的具体实现协议。MySQL、Oracle 等数据库都实现了 XA 接口。但 XA 同样是同步阻塞的，且要在数据库层面持有锁直到全局提交，高性能场景很少用。

6.4 TCC：业务层的两阶段提交

TCC 的本质：把「两阶段提交」从数据库层搬到业务层。Try 是预留（冻结而非扣减），Confirm 是最终确认，Cancel 是反向补偿。

2PC / XATCC
锁的粒度数据库行锁 / 表锁，一直持有到全局提交业务层的逻辑冻结，不长期占数据库锁
性能低，同步阻塞较高，但需要改造业务
侵入性低（框架透明）高，每个参与方都要写三个方法
一致性强一致（但有失败窗口）最终一致
适用短事务、内部系统金融、支付等对一致性要求高的场景

6.5 可靠消息最终一致（RocketMQ 事务消息）

本地消息表是同一思路的「土办法」：把「业务操作」和「往消息表插一条记录」放在同一个本地事务里，然后由定时任务扫描消息表把消息发出去，发送成功就标记完成。优点是实现简单、不依赖特定 MQ；缺点是多了轮询、实时性差。

这类方案能成立的两个前提：① 本地事务和消息投递之间靠回查 / 轮询兜底，保证「一定会发出去」；② 消费端必须幂等，因为消息可能重复投递（至少一次语义）。

6.6 Saga：长事务的补偿链

Saga 把一个长事务拆成 N 个本地事务 T1...Tn，每个 Ti 配一个补偿操作 Ci。依次执行，一旦第 k 步失败，就反向执行 Ck-1 ... C1 回滚前面已完成的步骤。

正向编排 vs 反向补偿
优点无长锁、性能好，适合流程长、跨多个服务的业务
缺点没有隔离性，中间状态对外可见；补偿逻辑必须自己写且要幂等
实现Seata Saga 模式、Temporal、Camunda 等工作流引擎

6.7 Seata 的四种模式

模式原理特点
AT（默认，最常用）拦截 SQL，自动记录 undo log；提交时先注册全局锁，回滚时用 undo log 反向补偿对业务几乎无侵入，适合大多数场景
TCC业务自己实现 Try / Confirm / Cancel侵入大，但性能好、可控性强
Saga长事务编排 + 补偿适合长流程、多参与者
XA数据库原生 XA 接口强一致，但性能差
Seata 的三个角色：TC（Transaction Coordinator，事务协调者，独立部署的 Server）、TM（Transaction Manager，发起全局事务的一方）、RM（Resource Manager，管理分支事务的资源）。TM 向 TC 申请开启全局事务拿到 XID，XID 沿调用链传播，RM 用 XID 注册分支。

6.8 方案选型

业务特征推荐方案理由
强一致、短事务、内部系统2PC / XA、Seata AT实现简单、一致性强，性能可接受
金融资金类、要求高一致TCC可控性强，能精细控制资源预留与释放
跨服务、可接受最终一致可靠消息 / RocketMQ 事务消息解耦、异步，吞吐高
长流程（审批、履约）Saga避免长事务持锁，用补偿回滚
只要求「通知到位」最大努力通知实现最轻，如支付结果回调
答题加分点：主动说出「没有银弹」—— 所有方案的共同要求是幂等 + 可重试 + 可补偿 + 可观测。分布式事务的落地难点通常不在框架，而在补偿逻辑怎么写、重复消息怎么去重、悬挂怎么防。

6.9 高频追问速答

Q：为什么 TCC 需要「防悬挂」？
A：因为网络是不可靠的。Cancel 可能因为重试先于 Try 到达，如果 Try 之后才执行，就会冻结一笔永远不会被释放的资源。做法是记录事务状态，Try 执行前先判断该分支是否已被 Cancel。
Q：为什么要做空回滚？
A：Try 因为网络超时没到达参与方，但协调者认为失败并发起了 Cancel。此时参与方要识别出「这个分支根本没执行过」，直接返回成功，而不是报错导致补偿链断裂。
Q：分布式事务里「幂等」怎么实现？
A：常见四种 —— 唯一索引（数据库层兜底）、去重表（记录已处理的事务 ID）、状态机（只允许特定状态迁移）、Token 机制（先申请再提交，用一次就失效）。
Q：Seata AT 模式为什么需要全局锁？
A：AT 是先提交本地事务、后全局回滚的。如果在全局事务提交前，另一个全局事务修改了同一行数据，回滚时就会覆盖掉别人的修改。全局锁用来保证「同一条记录不会被两个全局事务同时操作」。
Q：如果消息消费失败怎么办？
A：MQ 自带重试（RocketMQ 默认 16 次、指数退避）；重试仍失败就进死信队列，由人工或补偿任务处理。同时业务侧要有对账兜底，比如定时任务扫描异常单据。

第 7 章Spring 与 Spring Boot

Spring 的面试题只有两个真正的难点：Bean 生命周期和循环依赖的三级缓存。其余（IoC、AOP、MVC、事务）只要能把流程说顺、把失效场景说全，就足够了。

7.1 IoC 与 DI

  • IoC（控制反转）：对象的创建、装配、销毁交给容器，程序不再自己 new。
  • DI（依赖注入）：IoC 的实现手段，容器把依赖「推」给对象。
  • 三种注入方式：构造器注入（推荐，能保证依赖不为空、便于测试、支持 final）、setter 注入（可选依赖）、字段注入（最简洁但难以测试，Spring 官方不推荐）。

7.3 循环依赖与三级缓存

什么是循环依赖：A 依赖 B，B 又依赖 A。如果不做处理，创建 A 时发现需要 B，创建 B 时又发现需要 A，无限递归下去。

三级缓存的边界（必答）：只能解决单例 Bean + setter / 字段注入的循环依赖。构造器注入的循环依赖解决不了 —— 因为对象还没实例化出来，根本没有机会提前暴露引用。原型（prototype）作用域的循环依赖也无法解决（Spring 会直接抛 BeanCurrentlyInCreationException）。

7.4 AOP 与动态代理

JDK 动态代理CGLIB 动态代理
前提目标类必须实现接口目标类不能是 final，方法不能是 final
原理基于接口生成 $Proxy 类，实现 InvocationHandler基于继承生成子类，实现 MethodInterceptor
Spring 的选择有接口时默认用 JDK 代理无接口时用 CGLIB；也可强制 proxyTargetClass=true
效率创建快、调用略慢创建慢（要生成字节码）、调用快

核心概念：切面（Aspect）、连接点（JoinPoint）、切点（Pointcut）、通知（Advice：Before / After / AfterReturning / AfterThrowing / Around）。

Spring Boot 2.x 起默认使用 CGLIB 代理（spring.aop.proxy-target-class=true）。原因是 CGLIB 不需要接口，能避免「目标类实现了接口但注入时用了具体类导致失败」这类问题。

7.5 @Transactional 的原理与失效场景

原理：@Transactional 的实现就是 AOP。容器为被标注的 Bean 生成代理对象，在方法调用前后由 TransactionInterceptor 开启 / 提交 / 回滚事务。

失效场景原因解决
方法自调用（同一类内 A 调 B）走的是 this，没经过代理对象注入自己、AopContext.currentProxy()、拆到另一个 Bean
方法不是 publicSpring 默认只对 public 方法生效（CGLIB 下 protected/包级也有限支持，但不可依赖）改成 public
异常被自己 catch 了异常没抛到代理层，事务拦截器认为执行成功catch 后重新抛出，或手动 setRollbackOnly()
抛出检查异常默认只对 RuntimeException / Error 回滚@Transactional(rollbackFor = Exception.class)
多线程调用事务上下文绑定在 ThreadLocal 上，子线程拿不到子线程内开启自己的事务
类没被 Spring 管理自己 new 出来的对象不会生成代理交给容器管理
传播行为设置不当如外层 REQUIRED、内层又 catch 了异常理解 REQUIRES_NEW / NESTED 的语义差异
回滚规则要记牢：默认只对 RuntimeException 和 Error 回滚，对检查异常（Exception 的直接子类，如 IOException）不回滚。所以生产代码里统一写 @Transactional(rollbackFor = Exception.class) 是最稳妥的做法。

七种传播行为（记住最常用的四个）

传播行为语义
REQUIRED（默认）有事务就加入，没有就新建
REQUIRES_NEW总是新建事务，挂起外层事务（内层回滚不影响外层）
NESTED嵌套事务，靠 savepoint 实现，内层回滚不影响外层
SUPPORTS有事务就用，没有就以非事务方式执行
NOT_SUPPORTED / MANDATORY / NEVER分别是不支持事务（挂起外层）/ 必须已有事务 / 必须没有事务

7.7 Spring Boot 自动配置

@SpringBootApplication 是三个注解的组合：

  • @SpringBootConfiguration：本质是 @Configuration，标记这是配置类。
  • @ComponentScan：扫描当前包及子包下的组件。
  • @EnableAutoConfiguration：触发自动配置。

自动配置的加载过程：

  1. @EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 引入选择器。
  2. 选择器读取类路径下 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（Spring Boot 2.7 之前是 spring.factories）里列出的所有自动配置类。
  3. 再用 @Conditional 系列注解过滤：比如 @ConditionalOnClass（类路径存在某类才生效）、@ConditionalOnMissingBean（用户没自己定义才生效）。
  4. 最终把满足条件的配置类注册成 Bean 定义。
一句话总结：自动配置 = 「把所有候选配置类读进来，再用 @Conditional 条件装配筛出当前项目真正需要的那些」。这也是为什么默认配置总能被你的自定义 Bean 覆盖 —— 因为有 @ConditionalOnMissingBean。

7.8 高频追问速答

Q：BeanFactory 和 ApplicationContext 的区别？
A：BeanFactory 是最基础的容器，懒加载（getBean 时才创建）；ApplicationContext 是它的增强版，启动时就预实例化单例 Bean，并且额外支持国际化、事件发布、资源加载、AOP 等企业级能力。
Q：Bean 的作用域有哪几种？
A：singleton（默认，容器内一个）、prototype（每次 getBean 都新建）、request、session、application、websocket。注意：prototype 的 Bean 容器不负责销毁。
Q：@Autowired 和 @Resource 的区别？
A：@Autowired 是 Spring 的，按类型注入，多个候选时配合 @Qualifier 或 @Primary；@Resource 是 JSR-250 标准，默认按名称注入，找不到名称再按类型。
Q：Bean 是线程安全的吗？
A：容器不保证。Spring 的单例 Bean 是共享实例，如果它有可变状态（成员变量），就需要自己做同步（用 ThreadLocal、无状态设计或加锁）。这也是 Service / Controller 通常写成无状态的原因。
Q：Spring 事务和 MyBatis 是怎么配合的？
A：Spring 通过 DataSourceTransactionManager 管理连接，把 Connection 绑定到当前线程的 TransactionSynchronizationManager；MyBatis 的 SqlSessionTemplate 从 Spring 拿这个连接，从而保证同一个事务内的多个 Mapper 调用复用同一个数据库连接。

8.3 项目经验题怎么答

面试官问「你在项目里怎么用的」，通常不是想听技术名词，而是想看你解决问题的过程。推荐这个四段式结构：

  1. 背景与问题：什么业务场景、原来的做法出了什么问题、量级是多少（有数字最好）。
  2. 方案对比：你考虑过哪几种方案，各自的取舍是什么，为什么最终选了这个。
  3. 落地细节：具体怎么改的，踩了哪些坑（这部分最加分）。
  4. 结果：量化收益，比如响应时间下降多少、QPS 提升多少、故障减少多少。
把八股接到项目上的三个万能锚点：
① 线程池：异步任务用了自定义线程池，做了业务隔离和队列积压告警。
② Redis：热点数据缓存，讲了过期时间加随机防雪崩、分布式锁用 Lua 释放。
③ 分布式事务：跨服务一致性用可靠消息 + 本地消息表，消费端用唯一索引做幂等。
